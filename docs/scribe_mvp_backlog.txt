1. Purpose of this Document
This document expands the approved Product Vision and MVP Scope into concrete, design-ready Kanban tickets. Each ticket contains enough detail for the team to design screens, flows, data models and technical behaviour without ambiguity.
We will use these tickets as the single source of truth while we design and build. Tickets can be refined further during design, but the intent and acceptance criteria should remain stable.
Kanban columns: Backlog → Ready → In Progress → Done
2. Locked Decisions (as of Version 1.1)
Design System Direction
•Feeling: Clean & professional + warm & friendly
•Typography: Clean sans-serif
•Density: Just right – show the information needed, when it is needed
•Colour: To be finalised later (current mockups use teal/green + black + soft neutrals)
•Explicit don’ts: No AI-generic gradients/neon, no emojis in the UI, no overly playful illustrations, no heavy AI-style copy. This is a serious tool.

Technical Stack
•Frontend: Next.js (React) + Tailwind CSS
•Backend: Next.js API Routes / Supabase Edge Functions
•Database + Auth + Storage: Supabase (Postgres, Auth, Storage, Row Level Security)
•Hosting: Vercel (Next.js) + Supabase (managed)
•Authentication: Hybrid – Magic Link and Email + Password
•Structure Extraction: Flexible – prefer free/cheap AI vision or document AI services (provider kept open)
•Final Output: Browser Print (user can Save as PDF or send to printer). No forced server-side PDF generation in MVP.
•Platform: Mobile-first web. PWA later only if teachers strongly request it.
•Cost philosophy: Free to extremely cheap services so the product can be free or very low-cost for schools.
3. Epic Overview
The MVP is organised into five epics:
1.Organisation & Access – accounts, roles, invitations, privacy
2.School Template – admin template editor with live preview
3.Teacher Exam Creation Flow – photo capture → extraction → review → print
4.Admin Exam Overview – view and print exams organised by class
5.Foundational / Cross-cutting – design system, tech stack, auth, mobile shell, data model
4. Epic 1 – Organisation & Access
Goal: Enable a school to create an organisation, invite teachers, assign roles, and enforce strict privacy isolation.
Ticket 1.1 – Create Organisation
Description
As a school admin I want to create a new organisation so that my school can start using Scribe under a single shared account.
Acceptance Criteria
•Admin can enter organisation name and basic details
•Organisation is created and the creator becomes the first Admin
•Organisation has a unique identifier
•After creation the admin is taken to a simple onboarding / dashboard
Design Notes
•Keep the form extremely simple (name + optional contact email)
•Organisation logo is handled inside the Template editor, not here
Ticket 1.2 – Invite Teachers
Description
As a school admin I want to invite teachers by email (or shareable link) so they can join my organisation and start creating exams.
Acceptance Criteria
•Admin can invite one or more teachers by email
•Invited teacher receives a clear invitation
•Teacher can accept and is automatically linked to the organisation
•Admin can see list of pending and accepted invitations
•Admin can revoke an invitation or remove a teacher
Design Notes
•Prefer magic-link style invite for simplicity
•Consider a temporary shareable invite link as an alternative
Ticket 1.3 – Roles & Permissions
Description
As the system I must enforce two clear roles so that teachers and admins only see what they are allowed to see.
Acceptance Criteria
•Two roles only in MVP: Teacher and Admin
•Teacher can create, review and print only their own exams
•Admin can manage template, invite teachers, and view/print all exams in the organisation
•Teachers cannot see other teachers’ exams
•Organisations are completely isolated from each other
Design Notes
•Keep role model extremely simple – no custom roles in MVP
•Privacy is a hard requirement – use Supabase Row Level Security from day one
Ticket 1.4 – Authentication
Description
As a user I need a simple and reliable way to sign in so that my work is private and I can return later.
Acceptance Criteria
•Support both Magic Link and Email + Password
•Session persists across app restarts on the same device
•Clear sign-out option
•Works well on mobile browsers
Design Notes
•Implemented via Supabase Auth
•Prioritise simplicity and low friction for non-tech teachers
5. Epic 2 – School Template
Goal: Allow school admins to define the official exam look-and-feel once, with a live preview, so every teacher-generated exam is consistent.
Ticket 2.1 – Template Editor Shell + Live Preview
Description
As a school admin I want a template editor with a live side-by-side preview so I can see exactly how the final exam will look while I make changes.
Acceptance Criteria
•Editor is split: controls on one side, live preview on the other (stacked on small screens)
•Preview updates immediately when any setting is changed
•Preview shows realistic sample questions, options, marks and multi-page layout
•Works on tablet and desktop; usable on large phones
Design Notes
•High-visibility screen – invest in polish and clarity
•On mobile the preview can be a toggle or bottom sheet if side-by-side is too cramped
Ticket 2.2 – Logo Upload, Resize & Position
Description
As a school admin I want to upload the school logo, resize it and position it in the header so the exam looks official.
Acceptance Criteria
•Admin can upload an image (PNG/JPG)
•Admin can resize the logo with simple controls
•Admin can choose position (left / centre / right)
•Changes appear instantly in the live preview
•Logo is stored in Supabase Storage and reused for all future exams
Design Notes
•Keep resize/position controls simple
•Provide guidance on preferred file size and aspect ratio
Ticket 2.3 – School Name Toggle & Address
Description
As a school admin I want to show or hide the school name text and add address/contact details so the header matches our official stationery.
Acceptance Criteria
•Toggle to show / hide school name text (useful when logo already contains the name)
•Fields for school address and optional contact details
•All changes reflected live in the preview
Design Notes
•Place the toggle next to the school name field for clarity
Ticket 2.4 – Header, Footer, Fonts, Margins & Numbering
Description
As a school admin I want control over header layout, footer content, fonts, margins and question numbering style so exams match our required format.
Acceptance Criteria
•Header layout options (logo + text arrangement)
•Footer: page numbers, optional fixed text
•Font family and size selection (limited sensible choices)
•Page margins control
•Question numbering style (1, 2, 3… or 1a, 1b… etc.)
•All changes update the live preview
Design Notes
•Limit font choices to 3–5 readable options
•Numbering style should be a simple dropdown
Ticket 2.5 – Exam Title Block Fields
Description
As a school admin I want to define which metadata fields appear at the top of every exam (subject, class, term, date, duration, total marks) so teachers fill them consistently.
Acceptance Criteria
•Configurable set of title-block fields
•Fields appear in the live preview with sample data
•When a teacher creates an exam they are prompted to fill the required fields
Design Notes
•Start with a fixed sensible set (Subject, Class, Term, Date, Duration, Total Marks) rather than fully custom fields in MVP
6. Epic 3 – Teacher Exam Creation Flow
Goal: Let a non-tech-literate teacher go from handwritten pages to a school-branded, print-ready exam in a few simple steps.
Ticket 3.1 – Multi-page Photo Capture / Upload
Description
As a teacher I want to take multiple photos of my handwritten exam (or upload from gallery) so that a multi-page exam can be processed as one document.
Acceptance Criteria
•Primary action is “Take Photo” using the device camera
•Teacher can add multiple pages
•Teacher can reorder or delete pages before processing
•Gallery upload is also supported
•Clear visual indication of how many pages have been added
Design Notes
•Mobile-first – large touch targets, clear “Add another page” button
•Show thumbnail strip of captured pages
Ticket 3.2 – Structure Extraction
Description
As the system I must extract questions, sub-questions, options, marks and basic structure from the uploaded photos so the teacher receives an editable structured exam.
Acceptance Criteria
•System detects individual questions and sub-questions
•Multiple-choice options are recognised where present
•Marks allocation is extracted when visible
•Basic reading order / page flow is preserved
•Teacher is shown a clear “Processing…” state and then taken to the review screen
Design Notes
•Highest technical risk item – plan for iterative improvement of accuracy
•Provider kept flexible (cheap AI vision / document AI). Abstract behind an interface so we can swap later.
•Diagrams treated as images in MVP (no redrawing)
•Show confidence or “needs review” indicators if helpful
Ticket 3.3 – Lightweight Structured Review Screen
Description
As a teacher I want a simple screen where I can fix text, marks and question order so the final exam is correct, without needing a full word-processor.
Acceptance Criteria
•Each question is shown as an editable card/block
•Teacher can edit question text, options and marks
•Teacher can drag-and-drop to reorder questions
•Teacher can add or delete a question if needed
•Changes are simple and hard to break the structure
•Clear “Continue to Preview” action
Design Notes
•Most important UX screen for teachers – keep it extremely clear and forgiving
•Large touch targets, minimal options per question
•Avoid any feeling of a full document editor
Ticket 3.4 – Live Preview of Final Exam
Description
As a teacher I want to see a realistic preview of the final formatted exam before I print it so I can confirm it looks correct.
Acceptance Criteria
•Preview shows the exam using the school template
•Teacher can scroll through pages
•Teacher can go back to the review screen to make further changes
•Clear Print action
Design Notes
•Preview should feel close to the printed result (same fonts, spacing, header)
Ticket 3.5 – Print Final Exam
Description
As a teacher I want to print the finished exam (or save it as PDF via the browser print dialog) so I or the school can use it immediately.
Acceptance Criteria
•Print action opens the browser print dialog
•The printed/saved output uses the organisation’s current template
•All reviewed content appears correctly
•Exam is saved in the organisation so the admin can also access it
Design Notes
•No server-side PDF generation required in MVP
•User can choose “Save as PDF” or send to a real printer from the browser dialog
7. Epic 4 – Admin Exam Overview
Goal: Give school admins a clear, organised view of every exam produced by their teachers so they can track and print them easily.
Ticket 4.1 – View Exams Organised by Class
Description
As a school admin I want to see all exams grouped by class so I can quickly find and manage papers for each class.
Acceptance Criteria
•Exams are listed and grouped by class
•Each exam shows key info: subject, teacher, date created, number of pages
•Admin can expand/collapse classes
•Empty state is friendly when no exams exist yet
Design Notes
•Class comes from the exam title-block field the teacher filled
•Keep the list clean; search/filter can come later
Ticket 4.2 – Print Any Exam
Description
As a school admin I want to print any exam (or save it as PDF) so I can distribute or print it for the school.
Acceptance Criteria
•One-tap Print action that opens the browser print dialog
•Output uses the organisation template and current content
•Works reliably on the devices admins use
Design Notes
•Same print approach as the teacher flow – consistent and simple
8. Epic 5 – Foundational / Cross-cutting
Goal: Provide the technical and design foundation that all other features depend on.
Ticket 5.1 – Mobile-first Responsive Shell
Description
As a user I need the application to work well on phones first, while remaining usable on tablets and desktops.
Acceptance Criteria
•Primary flows are optimised for mobile viewport
•Navigation is simple and thumb-friendly
•Admin template editor degrades gracefully on smaller screens
Design Notes
•Design mobile layouts first, then scale up. Use Tailwind for consistency.
Ticket 5.2 – Core Data Model & Storage
Description
As the development team we need a clear data model that supports organisations, users, templates, exams and strict isolation.
Acceptance Criteria
•Entities: Organisation, User, Membership/Role, Template, Exam, ExamPage/Photo, Question (structured)
•All queries respect organisation and teacher isolation via Supabase Row Level Security
•Photos and logos stored in Supabase Storage
Design Notes
•Design the model with privacy as a first-class constraint
Ticket 5.3 – Basic Error Handling & Empty States
Description
As a non-tech user I need clear messages when something goes wrong or when there is nothing to show yet.
Acceptance Criteria
•Friendly empty states (no exams yet, no teachers invited, etc.)
•Clear error messages for photo upload failures, processing failures, network issues
•Never show raw technical errors to the teacher
Design Notes
•Tone should be calm, helpful and non-alarming
Ticket 5.4 – Design System & Visual Language
Description
As the team we need a simple, consistent design system so every screen feels coherent, calm and professional.
Acceptance Criteria
•Primary and neutral colour palette defined (final colours can still be tuned)
•Typography scale using clean sans-serif
•Spacing, button, card, form and feedback styles defined
•No emojis, no AI-generic gradients, no playful illustrations
•Living reference (even if simple) so new screens stay consistent
Design Notes
•Feeling: clean & professional + warm & friendly
•Density: just right – information appears when needed
Ticket 5.5 – Technical Architecture & Stack
Description
As the team we need the core technical decisions recorded and the project skeleton ready so feature work can proceed without re-deciding fundamentals.
Acceptance Criteria
•Stack locked: Next.js + Tailwind + Supabase + Vercel
•Auth configured for Magic Link + Email/Password via Supabase
•Row Level Security approach defined for teacher/org isolation
•Structure extraction abstracted so the AI provider can be swapped
•Print-based output approach confirmed (no server PDF required in MVP)
•Basic project structure and deployment path documented
Design Notes
•Prioritise simplicity, low cost and low operational hassle
•AI extraction provider kept open and behind an interface
